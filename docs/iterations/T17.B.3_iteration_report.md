## 3. Phase 0 — Diagnóstico técnico del bug bloqueante

### 3.1 Hipótesis de truncamiento: refutada

La hipótesis implícita del orquestador antes de la inspección de Phase 3.5 era que los parse-errors del smoke de T17.B.2 podrían deberse a truncamiento: el output del reporter se cortaría antes de completar el JSON al alcanzar el límite de `reporter_max_tokens = 500`. La inspección de los 4 raw outputs, documentada en `experiments/T17.B.2/parse_error_inspection.md`, refuta esta hipótesis de forma inequívoca.

Como señala la inspección:

> No es problema de max_tokens: los 4 outputs cierran limpiamente con `}` y fence ` ``` ` antes del límite de 500 tokens. Subir max_tokens no soluciona nada aquí.

Los cuatro outputs (#6119, #2627, #12682, #6100) terminan voluntariamente antes del límite. La extensión de `reporter_max_tokens` no modifica el comportamiento causante del fallo.

| Hipótesis | Evidencia de inspección | Veredicto |
|-----------|------------------------|-----------|
| Truncamiento por `max_tokens` | Los 4 outputs cierran limpios antes del límite en todos los casos | Refutada |
| Schema-strict por omisión de `notes` | 4/4 outputs omiten exactamente la clave `notes` | Confirmada |

### 3.2 Causa real: schema-strict en `_parse_reporter`

El método `_parse_reporter` de `agents/agent4_fulltext_split.py` valida el JSON generado por el reporter contra `REPORTER_REQUIRED_KEYS_V1`, que define 8 claves obligatorias sin excepción: `population`, `intervention`, `comparator`, `outcomes`, `study_design`, `publication_type`, `language` y `notes`. Si falta cualquiera de estas claves, el método retorna `None` y el sistema produce un fallback EXCLUDE con razón `"reporter schema invalid"`.

Los 4 outputs que fallan en el smoke de T17.B.2 producen JSON sintácticamente válido (`json.loads` no falla). El rechazo ocurre en la validación de schema: todos y cada uno de los 4 outputs emiten exactamente 7 de las 8 claves requeridas, omitiendo en todos los casos la clave `notes`.

| Paper | Etiqueta gold | Claves emitidas | Fallo |
|-------|--------------|----------------|-------|
| #6119 | EXCLUDE | 7/8, JSON válido, cierra limpio | Omite `notes` |
| #2627 | EXCLUDE | 7/8, JSON válido, cierra limpio | Omite `notes` |
| #12682 | INCLUDE | 7/8, JSON válido, cierra limpio | Omite `notes` |
| #6100 | INCLUDE | 7/8, JSON válido, cierra limpio | Omite `notes` + texto en chino |

### 3.3 Mecanismo: longitud del protocol V2 y comportamiento del modelo

El template V1 del reporter incluye la instrucción explícita para el campo `notes`: "máx 2 frases. Solo si el paper afirma explícitamente algo crítico para PICO. Si nada, 'ninguna'." Bajo protocol V1 compacto, el modelo respeta esta instrucción y emite el campo con el valor literal `"ninguna"`. Bajo protocol V2, el bloque `{pico_block}` del prompt es aproximadamente 3 veces más largo porque incluye la cita literal completa de Paula 2025 p. 3. Bajo esta carga adicional, Qwen 2.5-7B 4-bit interpreta la frase "Si nada, 'ninguna'" como autorización para omitir el campo cuando no hay información crítica que consignar, en lugar de emitir literalmente `"notes": "ninguna"`. El resultado es JSON conceptualmente completo en 7 campos pero técnicamente rechazado por el contrato de schema estricto.

### 3.4 AskUser 2026-05-21 y fix autorizado

El usuario autorizó el 2026-05-21, mediante AskUser, una única intervención: hacer la clave `notes` opcional en `_parse_reporter` con default `"ninguna"` si la clave está ausente en el JSON parseado.

La justificación literal del usuario:

> La causa diagnosticada es schema over-restrictive, no problema semántico del modelo. El prompt V1 del reporter ya dice que notes puede ser "ninguna" cuando no hay observaciones — el modelo está interpretando esto como "puedo omitir la clave bajo carga cognitiva mayor (prompt V2)". El parser debería respetar la intención original: clave notes opcional, default "ninguna" si falta.

## 8. Análisis del veredicto: refutación empírica del split

### 8.1 El split produce especificidad máxima a costa de sensibilidad mínima

El sistema split corregido alcanza spec=0.974 — la más alta de los tres sistemas comparados. A la vez, produce sens=0.089, inferior incluso al baseline V1 (sens=0.467) y dramáticamente inferior al baseline V2 (sens=0.756). El delta de especificidad entre columnas 2 y 3 es +0.190, pero el delta de sensibilidad es -0.667. El F1, que penaliza este desequilibrio, cae de 0.444 a 0.138.

La hipótesis arquitectónica pre-registrada en `T17.B.3_hypothesis.md` §5.2 era:

> Dividir la Phase B de A4 en dos sub-tareas secuenciales independientes [...] simplifica cada operación individualmente hasta el nivel en que el modelo puede ejecutarla de forma fiable, mejorando la sensibilidad del screening con respecto al baseline monolítico bajo el mismo protocol.

La predicción verificable era sens >= 0.65 con spec >= 0.80. La predicción se incumple: sens=0.089 << 0.65. El resultado dispara la regla pre-acordada en `T17.B.3_hypothesis.md` §5.3:

> Si el experimento refuta la hipótesis arquitectónica (sens < 0.55, spec >= 0.80): la limitación es del modelo operando bajo este tipo de tarea y no de la arquitectura monolítica. Iterar sobre la arquitectura del split no produce ganancia adicional.

Y la conclusión pre-acordada en §9.3:

> Si `V1_split_V2_fix < baseline_V2`: monolítico paradójicamente gana por ruido útil. A4 al cajón de A5 con justificación empírica.

### 8.2 Mecanismo: disciplina sin flexibilidad contextual

La paradoja del split es que funciona exactamente como fue diseñado, y eso es el problema. El reporter describe fielmente la población del paper (diabetes mellitus tipo 2, cancer survivors, osteoartritis, hipertensión, etc.) y el decider, al recibir un reporte JSON sin acceso al texto original, aplica el criterio de elegibilidad de `PAULA_SPORT_PROTOCOL_V2` con rigidez literal: cualquier condición crónica relevante dispara la verificación contra la regla operativa de Paula sobre "serious illness" vs "common chronic conditions". El decider, sin el contexto completo del abstract ni del full-text, no puede modular su juicio y clasifica como EXCLUDE con alta confianza.

El monolítico V2, en cambio, toma la decisión en el mismo paso que describe el paper. El modelo accede simultáneamente al texto completo (truncado a 6.000 caracteres) y al protocol. Esta simultaneidad le permite incorporar señales de contexto que el decider del split nunca ve: si un abstract menciona "T2DM but community-dwelling adults aged 58 years", el modelo monolítico puede modular entre la comorbilidad (señal de exclusión) y la descripción de la población (señal de inclusión). El decider del split recibe solo los campos del reporte JSON y decide sin ese contexto.

La comparativa entre columnas 2 y 3 muestra que los 30 TPs que el split pierde respecto al monolítico V2 (de 34 a 4) son papers donde el modelo monolítico, con acceso al texto completo, aplica el criterio V2 con flexibilidad contextual. El split los excluye con alta confianza porque el reporte JSON, limpio de contexto, los hace parecer no elegibles a simple vista.

### 8.3 Sobre la paradoja del κ

El κ del split (0.090) es ligeramente superior al del monolítico V2 (0.050). Este dato no debe interpretarse como evidencia de que el split funciona mejor. El κ de Cohen es sensible a la distribución de predicciones positivas: el monolítico V2 produce 108 predicciones positivas (de las cuales 34 son TP), lo que infla el acuerdo esperado por azar y deprime el κ. El split produce solo 13 predicciones positivas (de las cuales 4 son TP), lo que reduce el acuerdo esperado y sube el κ marginalmente. La métrica primaria pre-registrada es la sensibilidad condicional a especificidad >= 0.80, no el κ. La paradoja de Feinstein-Cicchetti hace que el κ sea inadecuado como primaria en este contexto de prevalencia baja y sesgo de predicción cambiante entre sistemas.

## 9. Caso #6100 — limitación reconocida no abordada

El paper #6100 (gold=INCLUDE) presenta un comportamiento documentado a lo largo del bloque T17.B. En T17.B.2, el reporter producía output parcialmente en chino, lo que además omitía `notes` y causaba parse-error. En T17.B.3, el fix acepta el JSON (el campo `notes` se inyecta con default `"ninguna"`), pero el decider recibe un reporte con campos en chino y produce EXCLUDE con `confidence=low`.

El resultado final para #6100 en Phase 4 es un FN (gold=INCLUDE, predicted=EXCLUDE). La degradación idiomática del reporter bajo prompt V2 largo persiste como síntoma de la presión del modelo bajo carga de contexto, pero no fue abordada en T17.B.3.

La justificación de esta no-intervención es la consigna de mínimo cambio: T17.B.3 debía responder la pregunta arquitectónica con la menor cantidad de variables modificadas posible. Añadir una restricción de idioma al template del reporter habría cambiado el hash de prompt, invalidado el cache de T17.B.2 e introducido una variable adicional en la comparación columna 2 vs columna 3. La limitación se documenta aquí como deuda técnica abierta del módulo split, independientemente de si el split se descarta o no.

## 10. Phase 5 — Held-out: no ejecutado (condición pre-acordada)

La condición de ejecución automática de Phase 5, establecida en `T17.B.3_hypothesis.md` §8.4, era:

> Si y solo si V1 cae en Optimistic (sens >= 0.65 y spec >= 0.80), se ejecuta el held-out sobre N=166 sin AskUser. Cualquier otro veredicto → PAUSA AskUser, NO ejecutar held-out.

V1 obtuvo sens=0.089 < 0.55, veredicto PESSIMISTIC. La condición de ejecución automática no se cumple. El held-out sobre N=166 **no se ejecuta**. Esta decisión respeta el protocolo anti-HARKing: ejecutar el held-out sobre un sistema con sens=0.089 en dev no aportaría información adicional relevante y consumiría tiempo de GPU sin justificación metodológica.

## 11. Lecciones del bloque T17.B completo

### a) La pregunta de Eduardo Aguda tiene ahora una respuesta negativa clara

La pregunta formulada en la reunión del 2026-05-19:

> Un Qwen 2.5-7B cuantizado a 4-bit no monitorea consistentemente su propio razonamiento cuando se le pide describir un paper, aplicar criterios PICO, detectar auto-contradicciones y emitir una decisión binaria en una sola pasada. Dividir la Phase B de A4 en dos sub-tareas secuenciales simplifica cada operación hasta el nivel en que Qwen 2.5-7B puede ejecutarla de forma fiable.

La respuesta empírica del bloque T17.B es: no. El split no mejora el screening bajo el protocol correcto. La hipótesis de las sub-tareas más simples asumía que el cuello de botella era la complejidad metacognitiva del prompt monolítico. El bloque T17.B demuestra que el cuello de botella era el protocol, no la arquitectura. Una vez corregido el protocol, el monolítico alcanza sens=0.756, que supera al split por 66.7 pp. La "simplicidad" del decider no es una ventaja: es una privación de contexto que impide la modulación que el modelo monolítico aplica naturalmente.

### b) La disciplina del split y su reverso: obediencia sin modulación

El bloque T17.B.1 había observado que el split disciplinaba la obediencia al protocol: el reporter describía fielmente las comorbilidades y el decider las rechazaba con consistencia. En T17.B.1, este comportamiento se interpretó cualitativamente como favorable a la hipótesis arquitectónica. El bloque T17.B.3 muestra el reverso: esa disciplina, aplicada con el protocol correcto (que ahora admite comorbilidades comunes), se convierte en rigidez literal. El decider no tiene acceso al texto original y no puede distinguir entre "diabetes mellitus tipo 2 con adultos comunitarios de 58 años en una intervención de actividad física" (INCLUDE en gold) y "paciente diabético en cuidados primarios" (EXCLUDE). Los dos perfiles producen reportes JSON similares, y el decider los trata igual.

El modelo monolítico, paradójicamente, maneja esta ambigüedad mejor precisamente porque no puede separar la descripción de la decisión. Su "ruido cognitivo" es, en este contexto, información útil.

### c) El ciclo de tres bloques como demostración de metodología anti-HARKing aplicada

El bloque T17.B es el primer ciclo del proyecto que completó los tres sub-bloques de una misma pregunta con pre-registros independientes, confounds identificados y documentados, y un veredicto negativo honesto al final. T17.B.1 produjo evidencia favorable a la hipótesis bajo condiciones contaminadas (protocol incorrecto). T17.B.2 corrigió el confound y añadió un bug técnico bloqueante. T17.B.3 resolvió el bug y obtuvo el veredicto limpio: la hipótesis está refutada.

La narrativa completa es: el sistema aparenta funcionar mejor bajo split V1 con protocol V1 (sens 0.067 en dev, pero con disciplina cualitativa reconocible); el confound lo invalida. El baseline monolítico con protocol correcto alcanza sens=0.756 — la mayor ganancia del proyecto en un único cambio (28.9 pp). El split con protocol correcto alcanza sens=0.089 — peor que el baseline monolítico V1. La lección es que confundir "obediencia al protocol" con "mejora del screening" es un error analítico que solo se evita con comparaciones controladas y pre-registradas.

### d) El protocol como primera variable a validar en cualquier evaluación futura

Los tres bloques T17.B confirman, de formas distintas, la misma regla operativa: antes de cualquier evaluación, el protocol implementado en código debe compararse contra el documento de autoridad (paper publicado, PROSPERO, protocolo PRISMA). Esta validación cuesta minutos; omitirla costó dos bloques de ejecución con resultados no interpretables. La secuencia `ceiling analysis → pre-registro → smoke → Phase 4` establecida en T17.B.2 y mantenida en T17.B.3 es el procedimiento que debería seguirse en evaluaciones futuras del proyecto.
