## 2. Diagnóstico técnico: causa real del parse-error (Phase 0 completada)

### 2.1 Hipótesis técnica del prompt original: refutada

La hipótesis de partida implícita en el prompt automático del orquestador,
antes de la inspección manual, era que los parse-errors podrían deberse a
truncamiento: el output del reporter se cortaría antes de completar el JSON
al alcanzar el límite de `reporter_max_tokens = 500`.

La inspección de los 4 raw outputs del smoke de T17.B.2 — documentada en
`experiments/T17.B.2/parse_error_inspection.md` (Phase 3.5) — refuta esta
hipótesis de forma inequívoca:

> No es problema de max_tokens: los 4 outputs cierran limpiamente con `}` y
> fence `` ``` `` antes del límite de 500 tokens. Subir max_tokens no
> soluciona nada aquí.

Los cuatro outputs (#6119, #2627, #12682, #6100) terminan voluntariamente antes
del límite. La extensión de `reporter_max_tokens` no modifica el comportamiento
causante del fallo.

| Hipótesis del prompt | Evidencia de inspección | Veredicto |
|---|---|---|
| Truncamiento por `max_tokens` | Outputs cierran limpios antes del límite en los 4 casos | **Refutada** |
| Schema-strict por omisión de `notes` | 4/4 outputs omiten exactamente la clave `notes` | **Confirmada** |

### 2.2 Causa real: schema-strict en `_parse_reporter`

El método `_parse_reporter` de `agents/agent4_fulltext_split.py` (L365-389)
valida el JSON generado por el reporter contra `REPORTER_REQUIRED_KEYS_V1`,
que define 8 claves obligatorias sin excepción: `population`, `intervention`,
`comparator`, `outcomes`, `study_design`, `publication_type`, `language` y
`notes`. Si falta cualquiera de estas claves, el método retorna `None` y el
sistema produce un fallback EXCLUDE con razón "reporter schema invalid".

Los 4 outputs que fallan en el smoke de T17.B.2 producen JSON sintácticamente
válido (`json.loads` no falla). El rechazo ocurre en la validación de schema:
todos y cada uno de los 4 outputs emiten exactamente 7 de las 8 claves
requeridas, omitiendo en todos los casos la clave `notes`.

| Paper | Etiqueta gold | Claves emitidas | Fallo |
|---|---|---|---|
| #6119 | EXCLUDE | 7/8, JSON válido, cierra limpio | Omite `notes` |
| #2627 | EXCLUDE | 7/8, JSON válido, cierra limpio | Omite `notes` |
| #12682 | INCLUDE | 7/8, JSON válido, cierra limpio | Omite `notes` |
| #6100 | INCLUDE | 7/8, JSON válido, cierra limpio | Omite `notes` + texto en chino |

### 2.3 Mecanismo: longitud del protocol V2 y comportamiento del modelo

El template V1 del reporter incluye la instrucción explícita para el campo
`notes`: "máx 2 frases. Solo si el paper afirma explícitamente algo crítico
para PICO. Si nada, 'ninguna'." El modelo, al recibir el prompt V1 compacto,
respeta esta instrucción y emite el campo con el valor literal `"ninguna"`.

Bajo protocol V2, el bloque `{pico_block}` del prompt es aproximadamente 3
veces más largo que bajo protocol V1, porque incluye la cita literal completa
de Paula 2025 p. 3 en lugar de los campos compactos del protocol V1. Bajo
esta carga de prompt adicional, Qwen 2.5-7B 4-bit interpreta la frase "Si
nada, 'ninguna'" como una autorización para omitir el campo cuando no hay
información crítica que consignar, en lugar de emitir literalmente la cadena
`"notes": "ninguna"`. El resultado es JSON conceptualmente completo en 7
campos pero técnicamente rechazado por el contrato de schema estricto.

Este comportamiento es coherente con el fenómeno documentado en T17.B.2 §8.b:
la combinación de parsers de schema estrictos y prompts largos es arriesgada
en LLMs cuantizados a 4-bit. Cuando el prompt crece, el modelo puede omitir
campos que considera opcionales en contexto aunque el template los declare
obligatorios.

### 2.4 El caso #6100: síntoma adicional, no causa principal

El paper #6100 presenta un síntoma adicional: además de omitir `notes`, el
reporter cambia a chino a partir del campo `population`, produciendo un JSON
donde los valores de 7 campos aparecen en chino o en mezcla de idiomas. Esta
degradación idiomática es sintomática de la misma presión bajo prompt largo en
un modelo multilingüe cuantizado, pero no es técnicamente la causa del
parse-error. La causa, como en los otros 3 casos, es la ausencia de `notes`.

T17.B.3, por decisión explícita del usuario (AskUser, 2026-05-21), no aborda
el síntoma de cambio de idioma. Este comportamiento se documenta como
limitación conocida del bloque. La justificación de esta decisión se detalla
en la sección 3.

## 3. Fix autorizado y justificación del usuario

### 3.1 Decisión cerrada: opción (i) sola, solo la clave `notes`

El usuario autorizó el 2026-05-21, mediante AskUser, una única intervención:
hacer la clave `notes` opcional en `_parse_reporter` con default `"ninguna"`
si la clave está ausente en el JSON parseado.

El alcance exacto de la modificación es:

- En `agents/agent4_fulltext_split.py`, dentro del método `_parse_reporter`
  (L365-389), antes del bucle de validación strict (L378-388), insertar la
  inyección condicional del default:

  ```python
  # notes es opcional en el contrato del prompt ("Si nada, 'ninguna'").
  # El modelo lo omite bajo prompt V2 largo; restauramos el default.
  if "notes" not in parsed:
      parsed["notes"] = "ninguna"
  ```

- El resto del schema permanece strict: cualquier otra clave de
  `REPORTER_REQUIRED_KEYS_V1` ausente sigue produciendo retorno `None` y
  fallback EXCLUDE.

El usuario descartó explícitamente las siguientes intervenciones:

- NO añadir 1-shot (*few-shot*) al template del reporter.
- NO modificar el template del reporter en ninguna otra forma.
- NO añadir restricción de idioma (caso #6100 chino queda como limitación
  documentada, no se aborda en T17.B.3).
- NO modificar el template ni el parser del decider.
- NO tocar el campo `exclusion_signals` ni la validación del schema V2 (V2
  no se ejecuta en esta sesión).
- NO modificar `config/agents.json` (la hipótesis de subir `reporter_max_tokens`
  está refutada y no se aplica).

### 3.2 Justificación literal del usuario

La justificación que motivó la elección de la opción (i) sobre las alternativas
(ii) y (iii) es la siguiente (cita textual del AskUser 2026-05-21):

> La causa diagnosticada es schema over-restrictive, no problema semántico
> del modelo. El prompt V1 del reporter ya dice que notes puede ser "ninguna"
> cuando no hay observaciones — el modelo está interpretando esto como "puedo
> omitir la clave bajo carga cognitiva mayor (prompt V2)". El parser debería
> respetar la intención original: clave notes opcional, default "ninguna" si
> falta.

### 3.3 Consecuencias del fix sobre el cache de T17.B.2

La opción (i) no modifica ningún template de prompt. El hash de prompt usado
por el orquestador `experiments/eval_a4_split.py` para identificar entradas de
cache se computa sobre el contenido del prompt renderizado (template + criterios
PICO inyectados + texto del paper). Al no cambiar el prompt, el hash de cada
entrada de cache es idéntico al producido por el smoke de T17.B.2.

Por tanto, los 11 papers del smoke de T17.B.2 que parsearon correctamente
tienen sus outputs ya en `experiments/T17.B.2/cache/reporter/`. Phase 3 de
T17.B.3 puede reutilizar esas entradas de cache si el orquestador lo soporta
y si se configuran los directorios de cache apropiadamente. Los 4 papers que
fallaron en T17.B.2 (#6119, #2627, #12682, #6100) también tienen sus outputs
cacheados (el fallo era en el parser, no en el modelo), y ahora el fix permite
parsearlos correctamente sin re-ejecutar el LLM.

Esta es la ventaja operacional más relevante de la opción (i) frente a las
opciones (ii) y (iii): la cache de T17.B.2 se puede reutilizar íntegramente,
lo que puede reducir el tiempo de Phase 4 de ~2.5 h a ~30 min si el orquestador
implementa correctamente la reutilización de cache por hash.

### 3.4 Limitación reconocida: caso #6100 y salida en chino

La opción (i) hace que el JSON de #6100 sea aceptado por el parser: los 7
campos en chino más el campo `notes` defaulteado a `"ninguna"` superan la
validación de schema. El decider downstream recibirá un reporte con campos
en chino y producirá una decisión. La calidad de esa decisión puede verse
degradada por el cambio de idioma, pero este efecto no se aborda en T17.B.3.

El iteration report Phase 6 debe registrar explícitamente el caso #6100 como
limitación conocida no abordada, con la razón: la consigna de mínimo cambio
para responder la pregunta arquitectónica sin introducir nuevas variables.

## 5. Hipótesis

### 5.1 Hipótesis técnica (local a T17.B.3)

El parser `_parse_reporter` de `agents/agent4_fulltext_split.py` rechaza JSON
semánticamente completo cuando el modelo omite la clave `notes` bajo prompt V2
más largo. Este rechazo es un artefacto del contrato de schema estricto, no
una señal de degradación del razonamiento del modelo. Hacer `notes` opcional
con default `"ninguna"` restituye la intención original del template ("Si nada,
'ninguna'") y elimina los parse-error fallbacks inducidos por esta omisión.

**Predicción verificable**: tras el fix, los 4 papers que fallaron en el smoke
de T17.B.2 (#6119, #2627, #12682, #6100) parsearán correctamente, y la tasa
de parse-error del smoke sobre los mismos 15 papers descenderá por debajo del
umbral de fallo del 5% (gate `parse_rate ≥ 95%`).

### 5.2 Hipótesis arquitectónica (heredada de T17.B.1 y T17.B.2)

Una vez el módulo split es técnicamente sano, la hipótesis arquitectónica que
articula el bloque T17.B desde su formulación original es evaluable:

Qwen 2.5-7B cuantizado a 4-bit produce errores de metacognición en un prompt
monolítico que le exige describir un paper, aplicar criterios PICO, detectar
auto-contradicciones y emitir una decisión binaria en una sola pasada. Dividir
la Phase B de A4 en dos sub-tareas secuenciales independientes — *reporter*
(descripción estructurada sin decisión) y *decider* (evaluación de criterios
sobre el reporte estructurado, sin acceso al paper original) — simplifica cada
operación individualmente hasta el nivel en que el modelo puede ejecutarla de
forma fiable, mejorando la sensibilidad del screening con respecto al baseline
monolítico bajo el mismo protocol.

**Predicción verificable**: la sensibilidad de `V1_split_V2_fix` sobre dev
N=387 alcanza el umbral Optimistic (sens ≥ 0.65) con especificidad ≥ 0.80.
Si la predicción se cumple, la hipótesis queda confirmada. Si no se cumple, la
hipótesis arquitectónica queda refutada con el protocol correcto y A4 se
reclasifica al cajón de A5.

### 5.3 Consecuencias lógicas según resultado

Si el experimento **confirma** la hipótesis arquitectónica (sens ≥ 0.65,
spec ≥ 0.80): la mejora sobre `baseline_monolítico_V2` es atribuible a la
arquitectura del split, no al protocol ni al modelo en sí. El sistema split
queda como candidato de reemplazo de la Phase B de A4 en producción, pendiente
de validación sobre held-out.

Si el experimento **refuta** la hipótesis arquitectónica (sens < 0.55,
spec ≥ 0.80): la limitación es del modelo operando bajo este tipo de tarea y
no de la arquitectura monolítica. Iterar sobre la arquitectura del split no
produce ganancia adicional; la energía de mejora se redirige a caracterizar
los límites del modelo (cajón de A5).

Si el resultado cae en las franjas **borderline** ([0.55, 0.65), spec ≥ 0.80):
la arquitectura produce mejora marginal o moderada pero no alcanza el umbral
de confirmación completa. La decisión sobre continuar con las variantes de
Fase B (V2, V3, V4) queda supeditada a AskUser.

    `# DEPRECATED 2026-05-20 — T17.B.2`.

12. **Fix schema-tolerante limitado a `notes`**: solo la clave `notes` recibe

correctamente parseados.

### 8.2 Métrica primaria (Phase 4)

La métrica primaria es la **sensibilidad condicional a especificidad ≥ 0.80**.
Una variante es evaluable solo si spec ≥ 0.80; las variantes con spec < 0.80
caen en el escenario Inválido y requieren diagnóstico cualitativo antes de
continuar.

### 8.3 Gates de Phase 4 (V1 sobre dev N=387)

Los rangos son idénticos a los de T17.B.1 y T17.B.2. No se re-litigan.

| Gate | Rango sens | Spec | Acción |
|---|---|---|---|
| Optimistic | ≥ 0.65 | ≥ 0.80 | Split funciona. Held-out automático sin AskUser. Fase B solo con confirmación humana. |
| Borderline-alto | [0.60, 0.65) | ≥ 0.80 | PAUSA AskUser. Fase B solo con confirmación humana explícita. |
| Borderline-bajo | [0.55, 0.60) | ≥ 0.80 | Cierre con mejora marginal. NO se itera más allá de V4. |
| Pessimistic | < 0.55 | ≥ 0.80 | Split refutado. A4 se reclasifica al cajón de A5. |
| Inválido | (cualquiera) | < 0.80 | Diagnóstico cualitativo de FP antes de continuar. |

Los rangos son absolutos, no relativos al baseline-on-dev. El gate se evalúa
sobre las métricas absolutas de `V1_split_V2_fix`. El análisis del valor
añadido de la arquitectura es relativo a `baseline_monolítico_V2`.

### 8.4 Held-out condicional (Phase 5)

Condición de ejecución automática: si y solo si V1 cae en Optimistic (sens ≥
0.65 y spec ≥ 0.80), se ejecuta el held-out sobre N=166 sin AskUser. Cualquier
otro veredicto → PAUSA AskUser, NO ejecutar held-out.

Sea `Δdev = sens_V1_dev − sens_baseline_V2_dev` y
`Δheld = sens_V1_heldout − sens_baseline_V2_heldout`.

Si `Δheld < Δdev / 2`, se reporta explícitamente como sobreajuste detectado
en el informe de iteración, sin ajustar thresholds ni reinterpretar el
resultado.

### 8.5 Fase B (V2, V3, V4)

**Declaración explícita: Fase B (V2/V3/V4) NO se ejecuta esta noche bajo
ninguna circunstancia, independientemente del resultado de Phase 4.**

Si V1 cae en Optimistic, la acción es la ejecución automática del held-out
y la apertura de Fase B solo con confirmación humana explícita en la siguiente
sesión. Phase 6 emite el iteration report con los resultados de Phase 4 (y
Phase 5 si se ejecutó).
